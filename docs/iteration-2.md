# Следующая итерация по повторному аудиту

Основание - [воспроизведения](results/iteration-1/audit-regressions.json) и проверка действующего RBAC в отдельном mtc-review. Цель запускается после закрытия текущей итерации; до этого документ является подготовленным набором задач. Каждая задача получает отдельный русский коммит, проверку и запись результата.

| Задача | Подтвержденный дефект | Критерий приемки |
|---|---|---|
| 1. Владение ReplicaSet | `_previous_replicaset` и `revision_age_seconds` в healer/app/k8s.py сравнивают имя Deployment. ReplicaSet удаленного Deployment с тем же именем принимается за текущий | Возраст и откат учитывают UID текущего Deployment и текущую ревизию; сиротский ReplicaSet отвергается тестом |
| 2. Ограничение чтений API | `replicas`, `deployment_identity`, `deployment_ready` и другие чтения SDK не задают `_request_timeout` | Все обращения Kubernetes ограничены по времени; ошибка чтения запрещает действие и не дает ложного восстановления |
| 3. Проверка восстановленного состояния | KubernetesStore принимает корректный JSON со счетчиком `_actions=-1` | Некорректный бюджет, типы и временные значения отвергаются до изменения глобального состояния; валидный журнал после замены пода сохраняется |
| 4. Ограничение прав записи | Настоящий `kubectl auth can-i` разрешил healer patch и update Deployment payment, хотя алгоритм его не меняет | Patch только checkout/redis, ненужный update удален; реальные проверки разрешенных и запрещенных объектов сохранены |
| 5. Разделение экспериментов | В postmortem начало 1791326272.709 раньше новой инъекции 1791326336.458; внутренние 249.2 с относятся к объединенному журналу, внешний MTTR нового прогона 198.1 с | До инъекции подтвержден закрытый инцидент healer; незавершенное состояние блокирует новый прогон, разные прогоны не смешивают таймеры |

Эти находки не означают, что в проведенных экспериментах был изменен чужой ресурс или поврежден ConfigMap. Воспроизведение первых трех выполнено на управляемых объектах SDK. Проверка RBAC только читала действующие разрешения.

После исправлений выполняются тесты, полный CI, повторный аудит и обновление результатов. Новые задачи добавляются по подтвержденным дефектам, а не для увеличения числа компонентов.

Еще два пробела ТЗ оформляются следующей целью после этих пяти исправлений: доказательство удержания SLO при ограниченном сетевом отказе (полный разрыв сейчас нарушает его) и проверка полезности LLM на нескольких инцидентах. Уверенность в совпадении формата ответа модели не подменяет качество рекомендации. Подтвержденные полные отказы сохраняются как отрицательные опыты; допустимая область хаос-воздействия должна быть явно определена до проверки.
