# Следующая итерация по повторному аудиту

Основание - [воспроизведения](results/iteration-1/audit-regressions.json), проверка действующего RBAC в отдельном mtc-review и повторное чтение полного ТЗ. После закрытия предыдущей итерации в этом же чате запускается цель по всем семи задачам. Каждая задача получает отдельный русский коммит, проверку и запись результата. Ветка остается fix/sre-case-completion.

| Задача | Подтвержденный дефект | Критерий приемки |
|---|---|---|
| 1. Владение ReplicaSet | `_previous_replicaset` и `revision_age_seconds` в healer/app/k8s.py сравнивают имя Deployment. ReplicaSet удаленного Deployment с тем же именем принимается за текущий | Возраст и откат учитывают UID текущего Deployment и текущую ревизию; сиротский ReplicaSet отвергается тестом |
| 2. Ограничение чтений API | `replicas`, `deployment_identity`, `deployment_ready` и другие чтения SDK не задают `_request_timeout` | Все обращения Kubernetes ограничены по времени; ошибка чтения запрещает действие и не дает ложного восстановления |
| 3. Проверка восстановленного состояния | KubernetesStore принимает корректный JSON со счетчиком `_actions=-1` | Некорректный бюджет, типы и временные значения отвергаются до изменения глобального состояния; валидный журнал после замены пода сохраняется |
| 4. Ограничение прав записи | Настоящий `kubectl auth can-i` разрешил healer patch и update Deployment payment, хотя алгоритм его не меняет | Patch только checkout/redis, ненужный update удален; реальные проверки разрешенных и запрещенных объектов сохранены |
| 5. Разделение экспериментов | В postmortem начало 1791326272.709 раньше новой инъекции 1791326336.458; внутренние 249.2 с относятся к объединенному журналу, внешний MTTR нового прогона 198.1 с | До инъекции подтвержден закрытый инцидент healer; незавершенное состояние блокирует новый прогон, разные прогоны не смешивают таймеры |
| 6. Удержание SLO при хаосе | Полный сетевой разрыв и начало CPU spike нарушают SLO; пункт 5 ТЗ требует подтвердить его удержание | До опыта определена допустимая область отказа; устойчивость проверена реальными ограниченными отказами пода, сети и CPU с клиентскими ошибками, p95 и синтетикой; сигнал о воздействии получен; полные отрицательные опыты сохранены |
| 7. Полезность LLM | Защищенный JSON сохраняет факты, но совет о payment не обоснован выбранным инцидентом потери метрик | Ответы по нескольким инцидентам оценены по конкретности, связи с фактами и отсутствию выдуманного; неподтвержденный совет явно отклоняется или помечается; набор примеров, промпты и ограничения сохранены |

Эти находки не означают, что в проведенных экспериментах был изменен чужой ресурс или поврежден ConfigMap. Воспроизведение первых трех выполнено на управляемых объектах SDK. Проверка RBAC только читала действующие разрешения.

Ход выполнения: задача 1 исправлена. 17 проверок actuator прошли, включая сиротский ReplicaSet, другую ревизию того же Deployment и отсутствие текущей ревизии. Откат не отправляется API при несовпадении UID.

Задача 2 исправлена: чтения Kubernetes SDK ограничены таймаутом 5 секунд, как и записи. 112 проверок actuator, evidence и webhook прошли; таймаут чтения не вызывает запись, готовность не подтверждается ошибкой API.

Задача 3 исправлена: проверяются полный набор полей, типы, конечные неотрицательные времена, целочисленный бюджет, подтверждения, владельцы и журнал. Проверка выполняется до восстановления глобального состояния и перед записью. После первой записи ConfigMap помечается и потеря state.json не считается новой установкой. 205 тестов healer прошли; отрицательный бюджет, null/false, неполное намерение и конфликт записи не вызывают операции или сброс сохраненного снимка.

Задача 4 исправлена: реальные [18 проверок RBAC](results/iteration-2/healer-rbac.json) прошли. Patch checkout/redis разрешен, patch/update payment и update checkout запрещены; Secret и чужой Job недоступны. Проверка добавлена в полный CI. Ограничение динамических имен подов описано в runbook.

Задача 5 исправлена: подготовка и инъекция требуют закрытого сохраненного инцидента, готовности SLO и отсутствия ожидающего подтверждения, неопределенной операции или возврата масштаба. 39 проверок состояния и допуска эксперимента прошли. [Реальный повтор](results/iteration-2/incident-isolation.json) подтвердил новое начало журнала после инъекции, удаление медленного пода и MTTR 117.3 с. В новых результатах injected_at - начало команды инъекции, injection_api_accepted_at - ее завершение; прежние опыты сохраняют исходную методику.

Задача 6 проверена: [три реальных опыта](results/iteration-2/limited-chaos.json) удержали SLO в заранее заданном профиле. Клиентский p95 при убийстве пода / задержке сети / CPU - 130.3 / 200.6 / 172.4 мс; максимальный p95 сервиса в выборках - 197.4 / 242.5 / 190.5 мс. Получено 301 / 300 / 301 полных успешных ответов, ошибок и dropped iterations нет. Статус CRD и информационный алерт подтверждены в каждом опыте. [Образ и хеши кода](results/iteration-2/slo-runtime.json), [правила promtool](results/iteration-2/rules.json) и [область доказательства](runbooks/chaos-limited.md) сохранены; полные отрицательные отказы не переименованы в успешные.

После исправлений выполняются тесты, полный CI, повторный аудит и обновление результатов. Новые задачи добавляются по подтвержденным дефектам, а не для увеличения числа компонентов.

Уверенность в совпадении формата ответа модели не подменяет качество рекомендации. Подтвержденные полные отказы сохраняются как отрицательные опыты; допустимая область хаос-воздействия определяется до проверки. Накопление месячной истории SLO и уточнение индивидуального опыта команды остаются внешними условиями, которые нельзя заменить коротким прогоном или выдуманными сведениями.
