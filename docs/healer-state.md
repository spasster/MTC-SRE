# Состояние и операции healer

Проверка в реальном k3d: `scripts/verify-healer-state.py`. В `docs/results/iteration-1/healer-state.json` подтверждены сохранение лимита и cooldown после удаления медленного пода и замены healer, а также единственный владелец Lease при двух экземплярах. Проверка неопределенного ответа API выполнена отдельно в управляемом тесте; реальная потеря ответа API не моделировалась.

Рабочее состояние хранится в ConfigMap `heal/healer-state`: начало инцидента, ожидание подтверждения, лимит действий, cooldown, результаты восстановления и владелец масштабирования. ConfigMap переживает замену пода и не зависит от демонстрационного Redis. Удаление кластера удаляет и эти данные.

Lease `heal/healer-leader` допускает одного активного исполнителя. Каждый процесс имеет уникальный идентификатор. Продление и запись состояния проверяют `resourceVersion`; потерявший Lease процесс не может сохранить результат или начать запись через actuator. Резервный экземпляр возвращает webhook HTTP 503, чтобы Alertmanager повторил доставку. Проверка восстановления продлевает Lease каждые пять секунд. Перехват после отказа занимает до 30 секунд плюс интервал проверки.

Перед изменением Kubernetes сохраняется намерение операции. Оно резервирует лимит действий до обращения к API. Для Deployment записывается идентификатор операции в annotation; удаление пода защищено его UID. Если API вернул определенный отказ, резерв снимается. Если ответ потерян, операция остается `unknown` и новые изменения запрещены. После перезапуска healer сверяет annotation или отсутствие исходного UID; обнаруженный результат не вызывает повторного применения.

Если результат API наблюдается только после перезапуска, точное время принятия команды неизвестно. Оно не выдумывается; в журнале остается время подготовки и событие `operation_observed`. Подтвержденное восстановление по метрикам измеряется отдельно. Операция, результат которой установить не удалось, требует проверки оператором. Она не повторяется по таймауту.

Возврат масштаба требует сохраненных UID, generation и revision того Deployment, который масштабировал healer. Изменение релиза оператором отменяет автоматическое уменьшение даже при том же числе реплик. Перед каждой записью повторно проверяются Deployment и его `resourceVersion`.

Журнал содержит последние 100 операций и 200 событий; это ограниченный журнал учебного контура. Долговременная история действий дополнительно требует хранения журналов наблюдаемости. ConfigMap содержит техническое состояние и ID запроса подтверждения, а секреты бота и API остаются в Secret. У healer нет прав записи в другие ConfigMap или Lease.

Режим `memory` предназначен для управляемых тестов вне Kubernetes. Манифест рабочего healer явно задает `HEALER_STATE_BACKEND=kubernetes`; недоступность хранилища останавливает вмешательство. Повторное применение манифеста не обнуляет данные ConfigMap и поля Lease, записанные приложением.
