# Аудит SRE-платформы

## Аудит после пяти приоритетных исправлений

Проверены чистая установка по зависимостям, подтверждения Telegram, результаты действий Kubernetes, достаточность метрик и момент завершения MTTR. Первые пять изменений оформлены отдельными коммитами. Штатные и новые проверки healer: 80 успешно. Реальные запросы Kubernetes и Telegram в этих тестах заменены управляемыми ответами.

Подтверждённое поведение:

- ServiceMonitor применяется после установки и готовности CRD.
- Старые и просроченные кнопки не подтверждают новый запрос.
- Ошибка и пропуск отката не увеличивают счётчик действий и не подтверждают восстановление.
- Пустые и некорректные метрики не закрывают инцидент и не уменьшают число реплик.
- Принятие команды API и подтверждённое восстановление SLO измеряются отдельно; проверяется текущая ревизия Deployment.
- Проверка восстановления и отложенный scale-down выполняются независимо от Telegram.

Дополнительные замечания к следующему этапу:

1. Ответы HTTP 500 от payment не учитываются как ошибки зависимости в диагностике плохого релиза.
2. Ошибки Telegram могут завершить поток обработки подтверждений и включить токен бота в текст исключения HTTP-клиента.
3. Между созданием запроса подтверждения и его применением может измениться ревизия Deployment; требуется повторная проверка плана.
4. Вебхук healer пока не аутентифицирован, и отправитель resolved может инициировать уменьшение числа реплик.
5. Ubuntu не собирает системные журналы; mTLS и Blackbox Exporter отсутствуют.
6. Требуются воспроизводимые эксперименты MTTR, материалы демонстрации и обновление README по итоговому поведению.

Полный локальный запуск пока не проверен: Docker Desktop завершился с ошибкой служебного сокета dockerInference. Проверки этой среды продолжаются отдельно от изменений приложения.

## Повторный аудит

Проверены требования кейса 2 из исходного DOCX, текущий код, конфигурации, история коммитов и работающий отдельный стенд mtc-review. Дополнительно выполнена чистая установка на Ubuntu 24.04 в GitHub Actions. Последние проверки healer - 139 тестов, checkout - 12, payment - 6; всего 157. Управляемые тесты проверяют отказы API и Telegram; они не являются доказательством работы реального внешнего бота.

### Исправления по повторному аудиту

- Ошибки payment отделены от ошибок приложения checkout; HTTP 500 зависимости не вызывает необоснованный откат.
- Подтверждённый план повторно проверяет диагноз и идентичность Deployment; запись защищена resourceVersion.
- Webhook и статус закрыты Bearer-токеном. Telegram не выводит секретные URL и продолжает опрос после ошибки.
- Метрики запросов, синтетики и CPU проверяются на достаточность. Нет CPU throttle - нет удаления пода.
- Общее окно ожидания предотвращает повторные действия от разных алертов. Запоздавший firing при здоровом SLO не открывает новый инцидент.
- Healer не уменьшает чужое масштабирование, проверяет текущие реплики и resourceVersion перед записью. Ошибка scale-down оставляет повторную попытку.
- Неверная оценка локальной модели отделена от вычисляемого по метрикам slo_assessment. У ассистента запрещены patch, delete и чтение Secret.

### Границы заключения

Это работоспособный учебный контур, а не доказательство промышленной отказоустойчивости. Инциденты и ожидания подтверждения хранятся в памяти одного healer. Перезапуск теряет таймер и отменяет ожидающую кнопку; внешнее хранилище и HA не реализованы. Несколько экземпляров не координируются.

Метрики job=checkout рассчитаны на выделенный demo-контур; несколько независимых checkout в одном Prometheus потребуют дополнительной изоляции запросов. Системные журналы проверены на свежем Ubuntu в CI; Linux-host auditd на машине пользователя не настраивался. Docker Desktop этой машины завершился с ошибкой служебного сокета, поэтому локальный Kubernetes проверен с отдельным Docker Engine в WSL.

Не измерены месячная доступность, точный максимум RPS, точность LLM по набору инцидентов и минимальный объём RAM/CPU. Первый неудачный MTTR-прогон и перегрузка сохранены, не подменены удачными цифрами. Выданный текст LLM требует проверки человеком даже при успешном HTTP.

Имена, роли и стаж участников ожидают данных владельца. Реальные сообщения и кнопки внешнего Telegram-бота не отправлялись и не проверялись. Эти два пункта явно оставлены для подготовки подачи и внешней проверки; технический код и локальные артефакты готовы.
