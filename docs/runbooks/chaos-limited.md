# Проверка удержания SLO при ограниченном хаосе

Область задается до запуска: три реплики checkout и две payment, единственный клиент 2 RPS, 180 секунд на каждый опыт, 60 секунд прогрева, один убитый checkout, разрыв одного пути checkout -> payment на 120 секунд, CPU StressChaos с одним worker и нагрузкой 5% ядра на одном checkout на 120 секунд. Ресурсы checkout - 200m CPU и 256Mi RAM на реплику. Скрипт начинает с двух checkout, временно добавляет резерв и возвращает исходные две реплики после серии. Суммарный лимит checkout во время опыта - 600m CPU и 768Mi RAM. Фоновый клиент временно отключается и восстанавливается; Blackbox остается включен. Генерация LLM во время опытов запрещена методикой.

`python scripts/verify-limited-chaos.py --cluster mtc` сохраняет каждый исходный результат, статус CRD, все выборки Prometheus и итог клиента. Нужны p95 клиента и каждой выборки сервиса < 300 мс, 5xx <= 0.5%, успешные полные ответы >= 99.5%, не менее 359 запросов за 180 секунд, отсутствие потерянных итераций и свежая успешная синтетика. Клиент проверяет также тело HTTP 200; невалидный ответ входит в бюджет неуспеха. Убийство пода дополнительно подтверждается новым UID. К концу каждого опыта Deployment должен иметь три готовые реплики, после серии - исходные две. Возврат масштаба проверяет UID, generation, число реплик, собственную аннотацию и resourceVersion; чужое изменение запрещает запись. Ошибки очистки сохраняются и не дают успешного итога.

NetworkChaos использует action=partition и точные имена одного checkout и одного payment. До инъекции оба пути проверяются HTTP-запросом к порту метрик, без выполнения платежа. После инъекции выбранный путь должен стать недоступен, второй - остаться доступен. Дополнительно по порту платежа читаются счетчики и состояние endpoint Envoy: растут отказы соединения, неисправный endpoint исключен, а число успешных запросов резервного endpoint растет. Эта проверка исключает успех при неиспользованном сетевом воздействии. `--faults network` повторяет только сетевой опыт и сохраняет отдельный результат; полный CI всегда выполняет все три.

Healer только читает три именованных CRD. `AllInjected=True` экспортируется в отдельную метрику; `ChaosFaultObserved` подтверждает, что воздействие было применено. Это информационный сигнал о тесте, который не означает нарушения SLO и не запускает восстановление. Сигнал сверяется с настоящими выборками и итогом k6. Полный сетевой разрыв и перегрузка из прежних опытов остаются отрицательными результатами за пределами этой области.

Istio выбирает наименее загруженный checkout и разрешает до двух повторов GET только при connect-failure и refused-stream. Для POST /pay допускается один повтор по тем же причинам до приема операции приложением. Новое соединение создается на каждый запрос payment; connectTimeout=100ms и исключение endpoint по локальному отказу обеспечивают резервный путь. Повторы по 5xx и таймаутам ответа отсутствуют. Методика не доказывает месячный SLO или устойчивость при отказе всех зависимостей.

История: [исходная серия с задержкой](../results/iteration-2/limited-chaos.json) удержала SLO локально, но не проверяла требуемый разрыв. [Первый CI](../results/iteration-2/ci-delay/run.json) с двумя checkout нарушил минутный p95 после убийства пода: 317 мс при клиентском p95 198 мс. [Локальный разрыв с двумя checkout и двумя payment](../results/iteration-2/limited-partition.json) и [повтор с подтверждением резервного endpoint](../results/iteration-2/limited-partition-mesh.json) прошли. Эти записи сохраняют свои исходные условия и не заменяют проверку нового профиля с третьей резервной репликой.

Источники конфигурации: [политика повторов Istio](https://istio.io/latest/docs/reference/config/networking/virtual-service/#HTTPRetry), [пул соединений и исключение endpoint](https://istio.io/latest/docs/reference/config/networking/destination-rule/), [сетевая изоляция Chaos Mesh](https://chaos-mesh.org/docs/simulate-network-chaos-on-kubernetes/), [CPU StressChaos](https://chaos-mesh.org/docs/simulate-heavy-stress-on-kubernetes/), [подтверждение инъекции](https://chaos-mesh.org/docs/inspect-chaos-experiments/).

В первом повторе после оптимизации клиента [SLO удержан](../results/iteration-2/limited-client-reuse.json), но 359 успешных ответов из 360 были отклонены ошибочным дополнительным порогом 99.9%, хотя в README и бюджете SLO принято 99.5%. Проверка приведена к объявленному SLO; одно неуспешное завершение из 360 допустимо, два запрещены. Исходный отрицательный итог сохраняется. p95, синтетика, частота запросов, область инъекции и остальные ограничения не изменены. Последующий [полный прогон трех воздействий на 3f49a38](../results/iteration-6/ci-spike-failure/limited-chaos.json) прошел; весь CI этой версии остановился позже на допуске к новой CPU-инъекции. Итог текущей приемки находится в [аудите](../audit.md).
