# Синтетическая проверка checkout

`CheckoutSyntheticFailed` имеет severity `critical`. Blackbox каждые 15 секунд вызывает `/work` из mesh и проверяет HTTP 200, `status=ok` и `payment=ok`. Это проход по рабочей цепочке checkout -> Redis -> payment. Запрос увеличивает тестовый счётчик корзины; его нагрузка учитывается вместе с k6.

1. Проверить `probe_success{service="checkout"}` и `probe_duration_seconds{service="checkout"}` в Prometheus или на дашборде SLO.
2. Если серия отсутствует, проверить `kubectl get pods,servicemonitor -n obs`, затем лог контейнера blackbox и готовность его sidecar. `CheckoutSyntheticMissing` сообщает об отсутствии данных отдельно.
3. Если серия равна 0, открыть дашборд «Инцидент», проверить ошибки зависимостей, состояние Deployment и трейс неудачного `/work`.
4. При сети или ошибках payment восстановить причину по соответствующему runbook. Имя алерта не разрешает произвольный рестарт: healer собирает текущие метрики и применяет только известный сценарий.
5. Считать сервис восстановленным после успешных синтетических запросов и выполнения SLO. Healer требует `probe_success=1` с возрастом выборки не более 45 секунд. Доступный `/health` не проверяет зависимости.

Синтетическая доступность считается как `avg_over_time(probe_success{service="checkout"}[5m])`. Окно 5 минут предназначено для демо; для отчёта за период заменить его на согласованное окно и отдельно проверить полноту выборки. Среднее без проверки отсутствующих данных не доказывает выполнение SLO.
