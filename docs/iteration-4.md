# Дополнительные исправления владения, контракта и образов

Основание - [два воспроизведения и проверка прямых вызовов процессов](results/iteration-3/audit-regressions.json) на 24c22ec, без настоящих мутаций, и [реальный повтор make apps](results/iteration-3/image-update-regression.json) в отдельном mtc-review на d09338c. Подготовленные исправления перенесены в рабочую ветку внутри расширенной текущей цели перед новым полным CI. Каждый пункт получил отдельный русский коммит; приемка включает живые проверки, повторный аудит, документацию и push.

| Задача | Что доказано | Критерий приемки |
|---|---|---|
| 1. Владение очисткой эксперимента | Отказ wait_incident_closed до подготовки все равно вызывает delete NetworkChaos и scale checkout/healer. Исходное чтение не подтверждает владение будущим объектом и чужое число реплик не проверяется | До собственной мутации очистка не пишет в кластер. Удаляются только созданные этим запуском объекты с тем же UID. Возврат масштаба проверяет UID, generation, ожидаемые реплики, собственную отметку и resourceVersion; чужое изменение сохраняется. Неизвестная запись не повторяется; ошибка очистки сохраняет неуспешный JSON |
| 2. Контракт ответа payment | Настоящий HTTP-клиент с MockTransport принимает HTTP 200 с status=error, пустым объектом или не-JSON как ok | Успех требует корректного JSON с status=ok и данных трассировки по контракту приложения. Некорректный ответ учитывается как отказ зависимости и не возвращает payment=ok; ошибка не раскрывает тело ответа и не повторяет POST. Здоровый путь и параллельные trace_id сохраняются |
| 3. Прямые процессы эксперимента | Два subprocess.run - инъекция spike с заданным профилем и проверка наблюдаемости - обходят ограниченную оболочку cmd и не задают timeout | Оба процесса имеют конечное время в рамках опыта. Превышение времени дает неуспешный JSON и безопасную очистку, не разрешает повтор неизвестной инъекции и не печатает закрытые данные. Настоящее зависание в аудите не заявляется |
| 4. Обновление локального образа | В двух подах одной ревизии payment разные imageID и main.py. Docker payment:dev соответствует новому коду; повтор make apps сохранил generation=2 и оба прежних UID. Разница данного исходника ограничена двумя описаниями метрик, изменение пути запроса не выдумывается | Изменение собранного образа меняет шаблон пода и приводит к rollout. Повтор с тем же образом не вызывает лишний rollout. Готовность дополняется проверкой imageID и хешей фактического кода; старый образ дает отказ. Чужой UID, изменение шаблона и неизвестный ответ API сохраняются без слепой повторной записи |

Для первой задачи уже выполнена [настоящая проверка нового временного Job и отдельного Deployment](results/iteration-3/owned-api.json): старые UID/resourceVersion не удалили пересозданный Job, смоделированное чужое число реплик сохранено. Это проверка подготовленной копии, не завершенная приемка всей следующей цели.

[Первый повтор проверки ответа API](results/iteration-3/owned-api-response-initial.json) сохранил неуспех после проверки пересозданного Job; точная причина не зафиксирована. [Повтор того же исходника](results/iteration-3/owned-api-final.json) подтвердил сохранение пересозданного Job, чужого масштаба и применение UID/resourceVersion в DeleteOptions. Очистка обоих запусков завершена без ошибок. Повторный успех не объявляется объяснением первоначального отказа.

При последующей реальной проверке [очистка собственной инъекции была отклонена](results/iteration-4/state-owned-prototype.json): [generation выросло с 1 до 7 при том же UID](results/iteration-4/state-owned-cleanup-diagnostics.json), в установленном CRD NetworkChaos [нет status subresource](results/iteration-4/chaos-generation.json). Разделение status и spec влияет на учет generation по [правилам Kubernetes](https://kubernetes.io/docs/tasks/extend-kubernetes/custom-resources/custom-resource-definitions/#status-subresource). Подготовленная очистка сохраняет полный spec из ответа create; рост generation NetworkChaos допускается при неизменных UID, собственной отметке и этом spec. Чужая перенастройка запрещает удаление, DELETE проверяет свежий UID/resourceVersion. [Сверка через серверный dry-run и завершение очистки](results/iteration-4/owned-network-reconciled.json) прошли, исходный неуспех сохранен.

Для четвертой задачи [проверена подготовленная процедура на payment](results/iteration-3/image-update-summary.json): rollout создал две реплики с одним imageID и одинаковым кодом, повтор сохранил generation=4 и UID обеих реплик. [Первый повтор](results/iteration-3/image-update-summary-initial.json) без лишнего rollout, но с изменением generation, сохранен; из процедуры убрана ненужная запись совпадающего spec. Все компоненты и чистый CI потребуют отдельной проверки после переноса четырех исправлений в рабочую ветку.

После четырех исправлений выполнить подходящие тесты, реальную проверку цепочки запроса и восстановления в отдельном mtc-review, полный CI новой версии и аудит владения/контракта/образов. Новые задачи добавлять только после подтверждения. Порог SLO не изменять ради прохождения проверки. LLM остается средством анализа и подготовки отчетов, с пустым списком применяемых действий.

В рабочей ветке пункты реализованы отдельными коммитами: контракт payment 1dab722, прямые процессы 17383fa, владение очисткой 310eb6f, неизменные образы aca5d12. [Тесты рабочей ветки](results/iteration-4/current-branch-tests.json) прошли: 332 healer, 25 checkout и 6 payment до добавления нового CPU-профиля. Подготовленные результаты выше сохранены со своими исходными SHA, а приемка новой версии требует ее фактических образов и полного CI.
