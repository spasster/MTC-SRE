# Локальный SRE-ассистент

LLM - дополнительный режим кейса. Он объясняет текущую картину инцидента по метрикам Prometheus и состоянию demo Deployment. Ассистент работает отдельным подом, с отдельным ServiceAccount и RBAC только `get/list`. Правилу healer не требуется модель для автоматического восстановления.

После повторного чтения ТЗ назначение уточнено: `/report` помогает разобрать текущий снимок; `/postmortem` готовит черновик отчета по последнему инциденту в журнале healer. Практическая задача LLM - объяснить симптомы, сопоставить решения и подтверждения и перечислить проверки, которые еще нужны. Измерения, временная шкала, результаты API и рассчитанный MTTR возвращаются отдельными структурированными полями. Текст модели не меняет эти факты.

Для `/postmortem` добавлено единственное право `get configmap/healer-state` в heal. Права `patch`, доступ к Lease и чтение Secret запрещены. В промпт передается белый список полей, без ID оператора, callback ID, сырых ошибок и корзины. Отчет содержит до шести операций и 12 событий, с явным признаком сокращенной шкалы. Начало, принятие API и восстановление SLO не заменяются друг другом; потерянное подтверждение времени остается `null`.

Промпт отчета находится в `healer/prompts/postmortem.md`, контекст для него ограничен 4096 токенами. Проверка: `python3 scripts/verify-llm.py --kind postmortem --cluster mtc --output docs/results/postmortem.json`. Текст модели остается черновиком, который проверяет человек. Автоматическое применение LLM-рекомендаций не включено: это дополнительный, а не обязательный режим ТЗ.

```sh
make llm
kubectl auth can-i patch deployments -n demo --as=system:serviceaccount:heal:sre-assistant
kubectl auth can-i get deployments -n demo --as=system:serviceaccount:heal:sre-assistant
kubectl port-forward -n heal svc/sre-assistant 8082:8082
```

Первая проверка прав должна вернуть `no`, вторая `yes`. Запрос `POST /report` требует токен из Secret `healer-webhook`. Не добавлять токен в Git, журнал терминала или видео. Отчёт содержит исходные метрики, решение правил, текст локальной модели и пустой список применённых действий.

Ollama 0.35.1 и Qwen2.5 1.5B запускаются на CPU. Режим скачивает крупный образ и около 1 ГБ весов модели, требует дополнительных 4 ГБ RAM и диска. Для минимального запуска `make up-linux` модель не требуется. Во время сравнения MTTR генерацию лучше отключить, чтобы нагрузка CPU не меняла условия эксперимента.

Промпт хранится в `healer/prompts/incident.md`. В него передаются только числовые поля, признаки готовности и имена подов; токены, конфигурации Secret, сырые ошибки и содержимое корзины не передаются. Ответ ограничен 384 токенами, контекст 2048 токенами. Ошибка соединения или незавершённый ответ дают HTTP 503 и не меняют кластер.

Модель может ошибиться в причине и рекомендации. Фактом считается измерение, а не текст модели. Даже опасная рекомендация не может вызвать действие: у ассистента нет API применения, а RBAC запрещает запись. Ссылки: [Ollama 0.35.1](https://github.com/ollama/ollama/releases/tag/v0.35.1), [API генерации](https://docs.ollama.com/api/generate), [Qwen2.5](https://ollama.com/library/qwen2.5).

6 октября получен настоящий локальный ответ: [results/llm.json](results/llm.json). RBAC подтвердил get deployments=yes, patch deployments=no, delete pods=no и get secrets=no. Поле `actions_applied` пустое. Код отдельно вычисляет `slo_assessment` по измерениям; текст модели не может изменить эту оценку.

Первый ответ [results/llm-initial.json](results/llm-initial.json) ошибочно назвал нормальный p95 проблемой. После этого в промпт добавлены единицы измерения, пороги и готовая оценка SLO. Повторный ответ распознал healthy. Это один пример, не оценка точности модели; непроверенное пояснение по-прежнему требует человека.

Повторить проверку: `python scripts/verify-llm.py --cluster mtc`. Скрипт сохраняет только метрики, разрешения и текст ответа, без токенов. Генерацию запускать после нагрузочных экспериментов.
